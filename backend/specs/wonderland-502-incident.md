# 奇域接口 502 排查报告（2026-09-26）

**现象**：`https://ugc.070077.xyz/wonderland?guid=127344607235&type=comments`
页面加载时请求 `/api/v1/wonderland/replies?guid=127344607235` 返回
`{"detail": "上游请求失败"}`（HTTP 502）。

**结论**：**跨太平洋链路到国内上游 CDN 的 TCP/TLS 建连会成片卡死**（实测约 6.7%
的新建连接卡到超时），而原实现**每次请求都新建连接**，恰好把最脆弱的一步放在必经路径上。
改为连接池复用后，同一时间窗口下失败率降到 0/300。属于基础设施层的瞬时故障
被「无连接复用 + 重试覆盖不全」放大成了用户可见的 502，**不是业务逻辑 bug**。

---

## 一、证据链

### 1. 线上日志：502 全部发生在 wonderland 接口

服务端（海外部署节点，PM2 进程 `qx-be`，uvicorn :8000）访问日志统计：

| 时间窗口 | 接口 | 200 | 502 |
| --- | --- | --- | --- |
| 09-26 全天 | `/wonderland/replies` | 26 | 7 |
| 09-26 全天 | `/wonderland/level` | 2 | 2 |
| 09-26 全天 | 其他所有接口 | — | **0** |

故障呈**成簇出现**（一次 4 条并发请求同时 502，随后同 guid 请求全部恢复正常），
说明不是单请求逻辑问题，而是**服务器出网侧的短时故障**。

### 2. 关键判据：失败的请求根本没发出去

uvicorn 访问日志与 httpx 请求日志条数精确对齐：

```
replies 200 OK:       26
httpx reply/list 200: 26   ← 完全一致
replies 502:           7
httpx reply/list 502:  0   ← 502 的请求没有任何 httpx 请求记录
level 200 OK:          2
httpx level/full 200:  2
level 502:             2   ← 同样无 httpx 记录
```

httpx 只在**拿到响应后**才写 `INFO:httpx:HTTP Request: ...`。502 请求没有该日志，
证明失败发生在 **TCP 建连 / TLS 握手阶段**，请求尚未送达上游。

### 3. 服务器侧排除项

| 检查项 | 结果 | 是否可疑 |
| --- | --- | --- |
| 服务器位置 / RTT | 海外节点，到上游 CDN 43.242.166.x **RTT ≈ 224ms** | ⚠️ 链路长 |
| DNS 解析 | 连续 200 次解析 0 失败；systemd-resolved 正常 | 否 |
| 代理变量 | 进程环境无 `HTTP(S)_PROXY` | 否 |
| 文件描述符 | 仅 43 / 上限 1048576 | 否 |
| conntrack | 572 / 65536，无丢包记录 | 否 |
| 本地端口 / TIME_WAIT | 端口范围正常，TIME_WAIT 仅 4 个 | 否 |
| 进程重启 | 已运行 1d12h，`unstable_restarts=0`（累计 9 次） | 否 |
| 内存 / PSI 压力 | PSI memory avg300=0.03%，swap 有占用但无换入换出 | 否 |
| 上游响应 | httpx 日志中**上游从未返回非 200** | 否 |

> 注：机器 2 核 3.4G，uvicorn RSS 1.36G，swap 用量 2.1G，虽然紧张但
> PSI 显示无实际内存停顿，不是本次故障原因（可作为后续优化项）。

### 4. 复现实验（在线上服务器上执行）

对照组复刻线上行为（同一时间窗口、同一上游），唯一变量是**是否复用连接**：

| 组 | UA | 连接方式 | 结果 | p50 | max |
| --- | --- | --- | --- | --- | --- |
| A | httpx 默认 | 每次新建 | 120/120 ok | 728ms | 3177ms |
| **B** | 浏览器 UA | **每次新建** | **112 ok + 8 × ConnectTimeout** | 660ms | **15015ms** |
| **C** | 浏览器 UA | **连接池复用** | **120/120 ok** | **301ms** | **785ms** |

**B 组复现了线上故障**：8/120 = **6.7% 的新建连接卡死**，每条耗尽 15s 连接超时
（max 15015ms）。而**同样时段、同样的 C 组（复用连接）0 失败，且 p50 延迟降到 42%**。

随后把样本放大到 300 次、并把 `connect` 超时按修复方案收紧到 6s 再测一轮：

| 组 | 结果 | p50 | p95 | max | 失败率 |
| --- | --- | --- | --- | --- | --- |
| **复用连接**（加固后行为） | **300/300 ok** | **261ms** | **494ms** | **852ms** | **0.0%** |
| 每次新建连接（原行为） | 295 ok + 5 × ConnectTimeout | 645ms | 1525ms | 6467ms | **1.7%** |

这解释了「成簇 502」：链路进入坏状态时，所有新建连接一起卡死；恢复后一切正常。
复用连接后失败率归零，p50 提速 2.5 倍、p95 提速 3 倍。

## 二、原实现的三个放大因素

1. **每请求新建 `httpx.AsyncClient`** → 每次都要重做 DNS + TCP + TLS，
   把 6.7% 概率的建连故障放进了必经路径。
2. **重试覆盖不全**：只重试 `ConnectError / ConnectTimeout / ReadTimeout /
   RemoteProtocolError`，漏掉了 `ReadError`、`WriteError`、`PoolTimeout`
   等（都属于 `httpx.TransportError`）。命中漏网异常时**一次失败直接 502**。
3. **上游 429/5xx 不重试**：非 200 直接 502。
   另外 `connect=15s` 偏长，3 次重试最坏要 48s，容易顶穿 CDN 回源超时。
4. **失败无日志**：`上游请求失败` 只回给客户端，服务端不留痕，
   导致线上只能看到 502、查不出异常类型。

## 三、修复内容

改动文件：`backend/wonderland/router.py`（重写）、`backend/main.py`（2 处小改）

| # | 改动 | 作用 |
| --- | --- | --- |
| 1 | 模块级共享 `AsyncClient` 连接池（延迟单例 + 锁） | **消除建连故障**（复现实验 C 组：0/120，p50 301ms） |
| 2 | 重试范围扩大到 `httpx.TransportError` 全家族 | 覆盖 `ReadError`/`WriteError`/`PoolTimeout` 等漏网异常 |
| 3 | 上游 429/500/502/503/504 也重试 | 抖动可自愈，不再直接 502 |
| 4 | `connect` 超时 15s → 6s，重试退避 0.4s/1.0s | 3 次重试最坏 ~19s，稳在 CDN 回源超时预算内 |
| 5 | 补齐浏览器 `User-Agent` / `Referer` / `Origin` / `Accept` | 降低被上游风控重置连接的概率 |
| 6 | 每次重试 + 最终失败均写 `logger.warning/error`（含异常类型） | 下次故障可直接从日志定位 |
| 7 | `keepalive_expiry=30s` | 避免复用到上游已单方面关闭的陈旧连接 |
| 8 | `main.py` lifespan 退出时 `close_client()` | 优雅关闭连接池 |

### 验证结果

本地用与线上一致的 `httpx 0.28.1` 跑 8 组共 25 项断言，全部通过：

- 真实调用 `level` / `replies` 返回正常数据
- 连接池为单例、UA/Referer 已生效、关闭后可重建
- **故障注入**：`ReadError` ×2 → 第 3 次成功（旧实现不重试）
- **故障注入**：上游 503 ×2 → 重试后成功（旧实现直接 502）
- **故障注入**：持续 `ConnectTimeout` → 重试满 3 次 → 502 且 `detail` 正确
- 非法 guid → 400

## 五、后续建议

1. **上线后观察日志关键字** `wonderland 上游连接异常`，可确认线上实际异常类型分布。
2. 若仍偶发，可加**页面级降级**：第 1 页失败才 502，后续翻页失败则返回已采集数据
   （当前选择「失败即报错」，因为统计口径错误比报错更危险）。
3. 机器内存偏紧（3.4G / swap 2.1G / uvicorn 1.36G），
   建议复核 `max_memory_restart` 与其它常驻进程，避免长期运行触发重启。
4. CDN（腾讯 EdgeOne）回源超时若可调，建议确认其配置以便重试预算对齐。
